## ch3 收尾 · 08 向量数据库（11/09 周一，0.5h）

### 3.1 向量库的作用与四层架构

- **解决什么**：几百万条向量里找最相似的几条。暴力扫是 O(N·d)，每条 query 都要跟全库算一遍距离，规模一上来延迟就崩。向量库靠 ANN 索引（HNSW 图 / IVF 量化 / LSH 哈希）把查询压到近似对数级，代价是「近似」——可能不保证严格最近邻。
- **改我哪行**：`store.py` 里 `get_or_create_collection("kb_store")` 就是「建库」这个动作；索引层（HNSW）是 Chroma 内置的，我一行索引代码都没写。白嫖的东西要知道白嫖了什么——面试问「你怎么做的索引」，答案是「Chroma 内置 HNSW，我没调」，不是「我实现了 HNSW」。
- **哪里不懂**：待补（Chroma 的 HNSW 参数 ef / M 默认值是多少、什么时候需要调）

### 3.2 相似度度量：cosine / L2 / 内积

- **解决什么**：先定义「近」是什么，才谈得上找最近的。三种度量：cosine 只看方向（模长归一化后等于内积）、L2 看方向 + 长度、内积 = cos × |a| × |b|。
- **改我哪行**：建库时 `metadata={"hnsw:space": ...}` 没写 → Chroma 1.5.9 默认 **l2**（返回平方欧氏距离），而 `search.py` 按 `score = 1 - dist` 当 cosine 用 → 实际 `score = 2cos - 1`，cos < 0.5 的全被 `max(0, …)` 截成 0。
- **实测（真库 8 chunk，零 API 调用，拿库存向量当 query）**：

  | source | chroma_dist | 2−2cos | cos | 1−dist | 2cos−1 |
  |---|---|---|---|---|---|
  | 保修-04（自己） | 0.000000 | −0.000177 | 1.0001 | 1.0000 | 1.0002 |
  | 保修-05 | 0.829027 | 0.828089 | 0.5860 | 0.1710 | 0.1719 |
  | 退款-04 | 0.856284 | 0.855892 | 0.5721 | 0.1437 | 0.1441 |
  | 退款-05 | 1.093730 | 1.092967 | 0.4535 | −0.0937 | −0.0930 |

  结论三条：
  1. Chroma 返回的就是平方 L2（`dist = ‖a−b‖² = 2 − 2cos`，四位小数吻合；偏差来自模长 1.0002 ≠ 1）。
  2. 向量已归一化 → `1 − dist = 2cos − 1`，余弦 < 0.5 就变负数，被 `max(0, …)` 截断。W3 看到的 0.16–0.33「偏低」不是检索差，是数值被换了坐标系。
  3. **排序完全一致**（L2 与 cosine 是单调映射）。所以这个 bug 不影响召回结果，只影响 score 的可解释性——以后想做「score < 0.6 就不答」的阈值过滤，数值必须是真 cosine。

- **哪里不懂**：待补

## 双 bug 修复 + 重建库（11/10 周二）

### bug 1：collection 度量吃默认值（store.py）

- 旧代码 `get_or_create_collection(COLLECTION)` 不声明 `hnsw:space` → Chroma 默认 l2（返回平方欧氏）。
- 新增 `_open_collection()`：读 `coll.configuration["hnsw"]["space"]`，不等于 `cosine` 就 `delete_collection` 重建。
- 为什么必须删：collection 的度量建库时写进索引，**之后不可改**，`get_or_create_collection` 传新 metadata 会被**静默忽略**（实测：建 l2 → 再 get_or_create(cosine) → metadata 仍是 l2，不报错）。
- 重建零 API：8 条 chunk 文本没变 → `md5("模型名:文本")` 缓存键全部命中。
- 修后 score 实测：0.5842 / 0.4716 / 0.4664 / 0.6637 / 0.6295，全部落在 [0,1]，不再被 `max(0,…)` 截断。

### bug 2：source 标注错（chunk.py + test_kb.py）

- 旧逻辑：`current_section` 在判断长度**之前**就被更新，导致「已写满的块」被贴上**下一个**条目的号；跨条目块只记最后一个。
- 新规则三档：块内出现过 `##` 条目 → 取**第一个**；整块无标题 → 沿用上一块；都没有 → 留空。
- 旧断言 `assert "退款-02" in source` 把 bug 钉成了合同（块跨 01/02 且标 02 = 「期望行为」），改为 `== "退款.md#退款-01"`，并在 docstring 写明字符分块的已知缺陷与周四升级路径。

**结论必须分清两笔账**：

3. 三档全败的 4 题（物流-02 快递单号在哪查 / 账号-02 密码找回 / 物流-04 箱子破了 / #21 丢件+运费双出处）值得单独查：这几条都是**短条目**，256 档下它们和邻居条目被合并进同一个块，块标签只记首条目 → 永远召不回。周四 md 分块（一 chunk 一条目）应该能救前三条；#21 是双出处题，靠 rerank 或 W5 混合检索。

## Markdown 标题分块 + 四档对比（11/12 周四整块）

### 实现

- 新增 `chunk_by_heading()`：按 `##` 切，**一个 chunk = 一个条目**，source 天然唯一。
- 四个边界 case 先写成 4 条 pytest（红），再写实现（绿）：
  1. 一条目一块，source 不再跨条目
  2. 第一个 `##` 之前的前言：有正文才独立成块（`文件名#前言`），只有标题就丢
  3. 单条目超长 → 按段落二次切，多块共用同一条目号（source 不加后缀）
  4. 提不出编号的 `## 注意事项` → 不切块，并入上一块
- `store.py` 增加 `CHUNK_MODE` 并写进 collection metadata，与 `hnsw:space` 一起构成**配置指纹**；
  任一不符就删库重建。不加这个的话，旧的 8 个字符 chunk 会和新 22 个条目 chunk 混存在一个库里。
- 结果：主库 22 chunk（5+6+5+5 条目 + 1 个前言），17 passed。

### 四档召回率（22 条口径）

| 档位 | 切分方式 | chunks | 召回 | 召回率 |
|---|---|---|---|---|
| **md** | 按 `##` 条目 | 22 | **22/22** | **100%** |
| 256 | 字符 | 17 | 18/22 | 82% |
| 512 | 字符 | 8 | 6/22 | 27% |
| 1024 | 字符 | 4 | 3/22 | 14% |

分题型（md 档）：直答 6/6、措辞陷阱 4/4、跨条目 4/4、跨文档 5/5、否定边界 3/3。

md 档相对 256 档**救回 4 题**，全部是「短条目被合并」的直接后果：

| 题 | 问题 | 256 档 top1（错） | md 档 |
|---|---|---|---|
| #3 | 快递单号在哪里查 | 物流-01 发货时效 | 物流-02 ✔ |
| #4 | 密码忘了怎么找回 | 账号-01 注册登录 | 账号-02 ✔ |
| #14 | 签收时发现箱子破了 | 物流-05 丢件索赔 | 物流-04 ✔ |
| #21 | 丢件退款含运费吗（双出处） | 退款-03 | 物流-05 + 退款-03 ✔ |

### 结论三条

1. **召回率从 82% 打到 100%，唯一变量是切分粒度**：字符分块把 4~6 个条目揉进一块，块标签只能记一个条目号，其余条目等于「没有名字」，永远召不回。一 chunk 一条目后，每个条目都有了独立向量，检索任务从「找一段包含答案的文本」退化成「22 选 3 的指认」，难度骤降。
2. **这不是调参调出来的**：四档里 256 是 82%、512 是 27%，说明字符分块下「块越大越差」的规律没变；md 档赢的不是块大小，是**块边界与条目边界对齐**。
3. **100% 必须打问号，不能直接写进简历**。三条限定条件：① 语料只有 4 篇 22 个条目，22 选 3 的基线命中率本来就有 ~14%；② 评测题是我按语料自己写的（出题人偏置）；③ 题目几乎都在问「某个条目里的规则」，没有需要跨段推理的问题。真实场景要难得多——这正是 W5 要做混合检索 + 忠实度评测的理由。

## rerank 接入（11/12 周四下午，原定周五任务提前）

### 端点实测（先验环境再写代码）

4 组全部 200：`dashscope.aliyuncs.com` 与 `ws-xxx.maas.aliyuncs.com` 两个 host × `qwen3.7-text-rerank` / `gte-rerank-v2` 两个模型。
走 DashScope **原生协议** `POST {host}/api/v1/services/rerank/text-rerank/text-rerank`，
不在 OpenAI 兼容模式下 —— 所以 `host` 要从 `settings.base_url` 里剥掉 `/compatible-mode/v1`。

### 实现要点（`src/llm_cli/kb/rerank.py`）

- 入参 `candidates` 就是 `search()` 的返回值，返回结构完全一致 → `ask()` 里两者可无缝替换
- `score` 存 rerank 分（排序与分数自洽），原向量分留 `vec_score` 便于两阶段对比
- `top_n = min(top_k, len(documents))`，避免传超参数
- `candidates` 为空直接返回 `[]`，不发请求
- 非 2xx / 超时一律 **raise**，不静默降级
- 自己按 `relevance_score` 降序排一次，不依赖服务端顺序（防御性）

### 增益数字（22 条，检索 top20 → rerank → top3）

| 指标 | 直接 top3 | rerank 后 | 口径 |
|---|---|---|---|
| top1 命中率 | 90% | **95%** | 20 条单出处题（双出处题没有唯一第一） |
| top3 召回率 | 100% | 100% | 22 条全量 |
| 正解平均排名 | 1.27 | **1.14** | 只统计进榜的 |

- 修好 1 题：**#10「换新手机能登同一个号吗」** 账号-01（注册登录）→ 账号-04（多设备登录）
- 没修好 #7「耳机拆了还能退吗」：仍是 退款-01 在前。原因是 退款-01 有「未拆封」、退款-02 有「拆封后不适用」，**字面高度重叠、语义互斥**，交叉编码器也倾向那条讲主规则的
- **top3 已饱和（100%），rerank 的账只能记在 top1 和排名上**。+5pt / 0.13 名是真实但小的增益，别夸大

### 面试话术（照这个说，别吹）

> 「向量检索 top3 召回已经 100%，所以我量的是 top1 命中率：rerank 把 90% 提到 95%，正解平均排名从 1.27 提到 1.14。有一道『拆封能不能退』还是错的，因为两条规则的文本高度重叠、语义互斥，这类题 rerank 也救不了——下一步靠 prompt 约束或换更强的 rerank 模型。」
