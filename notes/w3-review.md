## 五、本周最重要的实验结论

**三档分块对照实验**（面试核心弹药）：

| chunk_size | chunks | 召回率 |
|---|---|---|
| 256 | 17 | 50% |
| 512 | 8 | 25% |
| 1024 | 4 | 10% |

- **表面结论**：chunk_size 越小召回越高，ch2 理论量化验证
- **真实根因**：不是 chunk_size，是**条目号标注 bug**——多条目合进一个 chunk 时 source 只标最后一个条目号。直答题基线三档都差（17%/17%/0%）是证据
- **验证**：检查 256 档切分明细，保修条款 chunk[0] 含保修-01 内容但 source 标成保修-02
- **W4 优化方向**：Markdown 标题分块（一 chunk = 一条目），source 标注自然就准

**面试讲法**：用 20 条评测集测了三档 chunk_size 召回率，发现根因不是 chunk_size 是条目号标注 bug，优化方向是 Markdown 标题分块。

## 七、复现闸诚实记录

复现闸是 chunking 退回带做的唯一补救。用户不看代码手写了 chunk_document + 检索：

- **chunk_document**：算法逻辑全对（累积/输出/overlap/收尾四环节全对），变量名混乱（current_chunk vs current、for i 但 body 用 para、chunks 未赋值）
- **检索**：偏离规格（写了 API 版 search 而非纯算法 cosine_search），但检索流程正确（embed query → Chroma query → 解包 → 距离转相似度）
- **判定**：通过。事后内化了算法逻辑
- **根因延续**：手写精度问题（变量名/方法名/中文括号）与 Dockerfile 两行挤一行同一根因——脑子有结构，落笔细节歪。两周三次出现（Dockerfile/LC49手写/复现闸），W4 需要针对性练手写精度
