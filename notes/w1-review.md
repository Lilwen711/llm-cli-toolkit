## 四、卡最久的三点，以及以后怎么快速定位

### 1. `&#8203;` 零宽字符（约 40 分钟）

**现象**：`python -m llm_cli` 什么都不输出、退出码 0、没有任何报错。

**根因**：从聊天气泡复制代码时，`__main__` 被变成了 `__&#8203;main__`（零宽空格实体）。
字符串比较永远不相等 → `if __name__ == "__main__"` 恒为假 → `main()` 一次没被调用。

**以后的定位顺序**：代码"看着对但就是不执行"时，先扫 `&#`、全角引号/括号/逗号、Tab 与空格混用。

**预防**：关键标识符（函数名、字符串常量）手打，别复制。

### 2. git 全局代理指向死端口（约 40 分钟）

**现象**：`gh repo create` 报 `Post "https://api.github.com/graphql": EOF`，看起来像被墙。

**根因**：`~/.gitconfig` 里 `http.proxy = http://127.0.0.1:7890`（Clash 默认端口），但那个端口没有程序在听。
而 `gh` 不读 git 配置，只认 `HTTPS_PROXY` 环境变量——两边不对齐。

**教训**：**全局代理配置是最容易变成隐性故障的一类设置**——软件一关，所有网络操作全断，但报错看起来像网络问题。
需要代理时用临时参数：`git -c http.proxy=... push`，不要写进全局配置。

### 3. `Settings.base_url` 缺类型注解 + 尾逗号（约 20 分钟）

**现象**：`TypeError: ... got <class 'tuple'>: ('https://...',)`

**根因**：两个错叠加——① 少写 `: str`，`@dataclass` 只认带注解的名字，否则只是普通类属性、不进 `__init__`；② 尾逗号把字符串变成单元素元组。

**报错离真因隔了一层**：它说"类型是元组"，但真正的问题是"你忘了写类型注解"。

## 五、三个已经能吃住的技术判断

**1. 4xx 不重试。**
实测过一个 400（prompt 里缺 `json` 字样）被重试 3 次，白等 3 秒，日志还写着"可重试"，误导排查方向。
判断口诀：**4xx 是你的问题，5xx 和网络是对面的问题。**

**2. 分层让变化可控。**
加 PDF 支持时，只动了 `loader.py` 的三处，`main` 和 `llm_client` 一个字没改。
换模型同理——只改 `complete()` 一个方法。**这是分层的唯一价值，不是"代码好看"。**

**3. 编码问题先分清"文件坏了"还是"读的人用错字典"。**
`out/a.json` 用编辑器打开正常、终端显示乱码 = PowerShell 的 `Get-Content` 按 GBK 解码 UTF-8 文件。
**文件一直是对的。** 分不清这一层，就会去改本来没坏的代码。
